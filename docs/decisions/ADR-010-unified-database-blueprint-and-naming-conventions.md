# ADR-010: Database Blueprint Standards, Naming Conventions & Snapshot Integrity
**Status:** Approved  
**Date:** 2026-09-28  
**Scope:** Schema Naming Standards, Constraint Conventions, Normalization & Legal Dossier Integrity

---

## Context
As VYASA consolidates into a single unified database with dozens of relational tables across Core and Veda domains, strict architectural standards are required to ensure:
1. Predictable constraint and index naming across Alembic autogenerated migrations.
2. Deterministic foreign key relationships and deletion cascades.
3. Legal integrity and evidentiary validity for official university dispute resolution and research governance.
4. Strict third normal form (3NF) relational hygiene combined with formally audited, deliberate snapshot denormalization for immutable official records.

---

## Decision

### 1. Naming Conventions Standard
All database objects must strictly adhere to the following PostgreSQL naming conventions:

| Database Object | Format | Example | Rationale |
| :--- | :--- | :--- | :--- |
| **Table Names** | Lowercase snake_case, plural, domain prefix (except Core baseline) | `nivaran_grievances`, `notifications`, `rig_synopses` | Clean sorting, clear domain ownership |
| **Primary Key Column** | Always named `id` of type `UUID` | `id UUID PRIMARY KEY DEFAULT gen_random_uuid()` | Universally consistent identifier across all models |
| **Foreign Key Column** | `<target_singular_name>_id` of type `UUID` | `grievance_id`, `user_id`, `assigned_authority_id` | Instantly identifiable relationship target |
| **Boolean Flags** | Verb prefix (`is_`, `has_`, `can_`) | `is_active`, `is_verified`, `is_sealed` | Self-documenting boolean state |
| **Timestamp Columns** | Verb-past or state-noun + `_at` with Timezone | `created_at`, `updated_at`, `resolved_at`, `sealed_at` | Enforces UTC timestamp consistency (`TIMESTAMPTZ`) |
| **Primary Key Constraint** | `pk_<table_name>` | `pk_nivaran_grievances` | Deterministic Alembic diffing |
| **Foreign Key Constraint** | `fk_<table_name>_<column_name>` | `fk_nivaran_grievances_student_record_id` | Unambiguous error diagnostics |
| **Unique Constraint** | `uq_<table_name>_<column_names>` | `uq_nivaran_authorities_vyasa_user_id` | Clear conflict constraint identification |
| **Check Constraint** | `ck_<table_name>_<rule_description>` | `ck_nivaran_grievances_priority` | Clear validation failure reporting |
| **Index Name** | `ix_<table_name>_<column_names>` | `ix_nivaran_grievances_status` | Consistent index tracking |

### 2. Normalization & Justified Snapshot Denormalization (The Legal Dossier Rule)
- **Default Hygiene:** All operational transactional entities must strictly adhere to **Third Normal Form (3NF)**. Relationships must be established via foreign keys rather than duplicating columns.
- **Intentional Snapshot Denormalization:** In institutional governance, dispute resolution, and doctoral thesis certifications, historical records must reflect the exact institutional identity of actors at the moment an official legal action transpired.
- **The Snapshot Suffix Standard:**
  - Where point-in-time preservation is legally required (e.g., student name on an official sealed E-File dossier, supervisor designation on a signed dissertation synopsis, authority title on an administrative order), fields MUST carry the explicit suffix `_snapshot` (e.g. `applicant_name_snapshot`, `department_snapshot`, `email_snapshot`, `designation_snapshot`).
  - Such columns are strictly write-once and immutable. If a user subsequently changes their legal name or department in Core `users` or `applicant_profiles`, historic sealed dossiers and status audit trails MUST remain unaltered to preserve legal evidentiary admissibility.

### 3. Deletion Behavior Rules (Referential Integrity)
- **Cascade Delete (`CASCADE`):** Permitted ONLY for transient or tightly-coupled configuration child records that have no independent institutional existence outside their parent entity (e.g., `user_roles` when `users` is deleted; `role_permissions` when `roles` is deleted; `notifications` when `users` is deleted; `nivaran_poll_options` when a draft poll is deleted).
- **Evidentiary Immutability & Restrict Delete (`RESTRICT` / `NO ACTION`):** Required for all authoritative governance records, legal filings, sealed dossiers, and historical audit entries. Deleting a user who has filed grievances (`nivaran_grievances`), issued rulings (`nivaran_approvals`), cast committee votes (`nivaran_committee_votes`), or signed records (`nivaran_signatures`) is **STRICTLY FORBIDDEN**. Furthermore, an official grievance case (`nivaran_grievances`) cannot be hard-deleted if sealed E-Files (`nivaran_efiles`) or formal status history (`nivaran_status_history`) exist. The database must raise a foreign key violation to prevent accidental destruction of university records.
- **Nullify (`SET NULL`):** Permitted only where an optional secondary assignment is unassigned without invalidating the record (e.g., `assigned_authority_id` when an authority profile is archived, provided history tables preserve the trail).

### 4. Query-Driven Indexing Standard
- **No Blanket / Universal Foreign Key Indexing:** Foreign keys are not automatically indexed by default. Every index must be justified by demonstrable high-frequency query patterns, high selectivity, or critical sorting requirements. Low-cardinality taxonomy lookups and append-only write-heavy tables without join query load must not be indexed arbitrarily.

---

## Consequences
- **Positive:**
  - Complete legal audit compliance with Indian University governance standards and RTI (Right to Information) mandates.
  - Predictable database migrations with standard Alembic naming conventions convention dict.
  - Zero accidental record loss for critical administrative decisions.
- **Negative:**
  - Slightly increased storage for snapshot columns; negligible compared to legal integrity guarantees.
